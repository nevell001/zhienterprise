# AGENTS.md

知企建站系统（ZhiEnterprise）— an enterprise website building system on the RuoYi-Vue 3.9.1 platform. Spring Boot 3.5.16 backend (Java 17, `jakarta.*` namespace, Spring Security 6) + Vue 3 + TypeScript 5.9 frontend. Requires MySQL 8.4 (not 5.x) and Redis 6.2+. Current version: v1.1.0.

## Commands

### Backend (root of repo)

```bash
mvn clean install -DskipTests      # compile all modules
cd zhi-admin && mvn spring-boot:run
mvn test -Dtest=ClassName          # single test
mvn test -Dtest=ClassName#method   # single method
mvn test -pl zhi-system            # one module
mvn checkstyle:check               # style gate (runs on validate; checkstyle.xml)
```

`.env` 由 `application.yml` 的 `spring.config.import`（`optional:file:./.env[.properties]` + `../.env` 兜底）加载，从仓库根或 `zhi-admin/` 启动都能读到；`spring-dotenv` 依赖保留但不再是加载主路径。改 `.env` 后需重启后端生效。

### Frontend (zhi-ui)

```bash
npm install
npm run dev              # port 3000
npm run build:prod
npm run test             # Vitest
npm run test:coverage
npm run lint:check       # ESLint
npm run format:check     # Prettier
```

### Docker / DB

```bash
docker compose -f docker-compose.dev.yml up -d
docker compose -f docker-compose.prod.yml up -d
mysql -u root -p zhienterprise < sql/00_init_database.sql
```

## Architecture

Multi-module Maven. Standard pattern: Controller → Service → Mapper (MyBatis), RuoYi conventions (`BaseController`, `@PreAuthorize` with `zhi:entity:action` strings, `AjaxResult`, `TableDataInfo`).

- **zhi-admin** — bootstrap. Entry: `com.zhi.RuoYiApplication` (port 8080). `@ComponentScan(basePackages = {"com.zhi", "com.zhi.system.controller"})`, excludes `DataSourceAutoConfiguration`/`RedisAutoConfiguration` (manually configured).
- **zhi-system** — business logic. Holds the 9 admin controllers (`*Controller` under `com.zhi.system.controller`) and MyBatis mappers/XML. Mapper XML: `zhi-system/src/main/resources/mapper/system/`.
- **zhi-framework** — Spring Security, JWT filter, interceptors, AOP aspects, Redis/Druid config.
- **zhi-common** — utils, constants, base domain objects, XSS/filters.
- **zhi-quartz / zhi-generator** — scheduled jobs / CRUD codegen.
- **zhi-ui** — Vue 3 + TS frontend. `views/site/` (public), `views/admin/`, `api/site/`, `api/system/`, `components/`, `router/`, `stores/`, `utils/`, `types/`.

Front-end public endpoints (site API) (`FrontController`, `ArticleController`, etc.) live in `zhi-admin/src/main/java/com/zhi/web/controller/site/` — distinct from the admin `*Controller` classes in zhi-system.

## Auth

Unified login via `UnifiedAuthController` (`zhi-admin/src/main/java/com/zhi/web/controller/auth/`):
- `POST /auth/login` — the only login endpoint for both admin and registered users (legacy `/login` and `/api/auth/login` are gone). Logout is Spring Security's `POST /logout`.
- `GET /auth/user/info` — current user with roles.
- `AuthController` (`/api/auth/*`) — registration + email code + password reset only.
- JWT in `Authorization` header. Site settings control features via `zhi_setting` table: `comment_enabled`（**企业官网定位：默认 `false`**）/ `comment_review`, `view_count_enabled`, `search_enabled`, `footer_enabled`, `copyright_enabled`, plus the 企业官网模式 keys `home_page_slug` / `nav_category_enabled` / `nav_tag_enabled`, and the brand images `site_logo`（自定义 Logo，优先于 `blog_avatar`）/ `site_banner`（企业首页 Hero Banner **轮播**：最多 5 张，逗号分隔存一个键，空则回退模板母题插画）。 **已随博客功能移除的键**：`like_enabled` / `share_enabled`（点赞、分享）、`sidebar_enabled`（右侧栏）、`nav_archive_enabled`（归档入口），以及更早下线的 `author_*` / `github_url` / `weibo_url` / `blog_author` / `blog_signature` / `zhihu_url` / `author_description` —— 它们已从 `FrontConfigKeys` 前台白名单、`FrontSettingController` 默认值与 SQL 种子中一并删除，**不要重新加回**。
- Dev: set `EMAIL_DEV_PRINT_CODE=true` to print verification codes to console instead of sending mail.
- Registration is gated by `sys_config.sys.account.registerUser` (**not** `zhi_setting`) and is **default-OFF**: `AuthController` and `SysRegisterController` both accept only the literal `"true"`, so `"1"`/`"on"` mean closed. Do NOT route it through `SiteSwitchUtils.isOn` / `isFeatureEnabled` (those are default-ON with the opposite rule) — the 站点设置 「用户注册」 card is the exception, reads `GET /system/setting/registration` (which applies the strict rule) and writes via `updateByKey`, whose `sys_config` mirror + `sys_config:<key>` cache eviction is what makes the toggle take effect. Toggling via raw SQL leaves the Redis cache stale.
- `sys_user.user_type` ('00' 系统用户 / '01' 注册用户) is the frontend's sole gate for admin surfaces: `Navbar.vue` / `SiteLayout.vue` show the 「管理后台」 entry only when `userType === '00'`. Both public registration paths must set `'01'` (`UserService`, legacy `SysRegisterService`) — and `SysUserMapper.insertUser` must persist the column: when it silently dropped `user_type`, registered users landed on the DDL default `'00'` and the frontend showed them admin UI (「管理后台」 → `/admin`). `SysUserMapperTest` (H2) locks the insert↔select round-trip.
- **个人中心已下线**（`/user/profile` 路由、`views/admin/system/user/user/profile/` 整目录、Navbar 与 SiteLayout 的入口均已移除）：该页曾承载「基本资料 / 修改密码 / 通知」三个 tab。**连带影响**：用户失去自助改密与改头像入口，通知只能看铃铛面板里的最近几条（「查看全部通知」已一并删除）。后端 `SysProfileController`（`/system/user/profile` 查询/改资料/改密/传头像）**保留**但前端已无调用方；若要恢复自助能力，重建页面即可复用。**「站点设置 → 个人信息」tab 也已移除**（`author_title`/`author_bio`/`author_location`/`personal_website`/`github_url`/`weibo_url` 六键）：关于页「负责人」区块、Person JSON-LD、页脚「社交平台」的 GitHub/微博、页脚联系邮箱展示、联系我们页邮箱项均已同步删除；其中 `blog_email` 因同属「联系方式设置」组（与 `contact_phone`/`contact_address` 同类）**保留**。**「站点信息」tab 的「站长」字段（`blog_author`）以及无消费方的 `blog_signature` 也已移除**：页脚版权署名因此改为**只取站点名称**（`© {{year}} {{blog_name}} · 保留所有权利`，见 `SiteLayout.vue` 的 footer-bottom），不再拼接个人名字/昵称；store 的 `getSiteAuthor` getter 一并删除。若将来需要可署名的版权抬头，请用 `blog_copyright`（版权信息，自由文本）而非重建个人字段。
  **博客凭据类页面已整体下线**：`/author/:id`（作者主页，`views/site/author/`）与 `/bookmarks`（我的收藏，`views/site/bookmark/`）连同路由、白名单（`permission.ts` / `utils/request.ts` / `SpaRouterController` / `WebMvcConfig`）与后端 `BookmarkController`+Service+Mapper+Domain+XML 一并删除（`zhi_bookmark` 表保留历史数据不删）。详情页的收藏按钮此前已移除，收藏功能无来源；若未来要做「关注/收藏」需重新设计入口与权限。
- **认证页（登录/注册/找回密码）统一为企业风格**：三页都包在 `SiteLayout` 里（企业模式自动带企业导航/页脚），共用 `zhi-ui/src/assets/styles/auth-enterprise.scss` 的 `ent-*` 类与 `--tpl-*` 变量层；品牌信息统一走 `composables/useAuthBrand.ts`（`site_logo` → `blog_avatar` → 站名首字，站名取 `blog_name`）。类名刻意不用 `.auth-card`/`.switch-item`/`.sub`：`theme-dark.css` 与 `mo-blog.scss` 对旧认证页类名写了 `!important` 暗色规则，复用会被棕色皮肤污染。深色模式由 `html.dark .tpl-site` 的变量重映射 + 共享表的 `html.dark .ent-auth-page` 覆盖负责（卡片色关系：页面 `--tpl-bg` → 卡片 `--tpl-surface`）。
- **文章详情页已去博客化**（`views/site/article/detail.vue`）：移除阅读进度条、文章目录（TOC，`components/ArticleTOC.vue` 已随之删除）、作者卡（头像/关注/获赞/评论数）、收藏按钮、阅读时长、标签云侧栏与侧栏迷你相关推荐；结构改为企业官网新闻详情：面包屑 → 分类/日期/阅读量 → 标题 → 摘要 → 封面 → 正文 → 关键词胶囊 → 相关阅读卡片（3 列）→ 咨询 CTA（`/contact`）→ 上/下一篇。评论区保留但受 `comment_enabled` 控制（默认关闭），其 `--mo-*` 深色重映射已收窄到 `.comment-section`，不要再放大到整页（会把页面底色改成 `--el-bg-color` 的棕色）。另：`SimpleArticleResult` 与 `getPrevArticle`/`getNextArticle` 两条 SQL **必须 select `status`** —— 控制器要求 `status != null` 才输出导航项，漏掉会静默不显示上/下一篇（`ArticleNavigationQueryTest` 守卫）。
- Email codes: `verifyCode` is brute-force protected via Redis fail-counter per `email:codeType` (`max-verify-attempts`, default 5; locked for `verify-lock-minutes`). `FrontController` POST `/comment` and `/article/view/*` are IP rate-limited via `@RateLimiter` (60s / 10 req / IP); `UnifiedAuthController` `POST /auth/login` is IP rate-limited (60s / 20 req / IP); every `/common/upload*` endpoint is IP rate-limited (60s / 20 req / IP).
- Public stats: `GET /api/stats/overview` (`@Anonymous`) exposes published article/category/tag/comment counts and total views for the public 关于 page. The full admin overview `GET /system-stats/overview` requires `statistics:overview:list` (`SystemStatsController`) — never call it from public pages.
- Guestbook (留言板): public `GET /api/message/list|count` + `POST /api/message` (`@Anonymous`, IP rate-limited 60s / 5 req, length-validated, nickname/content only; the public list query deliberately omits `email`/`ip`/`user_agent`). The POST also enforces an input time window: a graphic captcha (`code`+`uuid`, same switch as login — reuse `ICaptchaService.validateAndGetAgeSeconds`) younger than 3s is rejected with 「提交过快」, and each visitor (login `userId`, else IP) gets one message per 60s via Redis `zhi:message:cooldown:<visitorKey>` (checked **before** the captcha, so a rejection does not burn the single-use code; the frontend shows a countdown on the button). Moderation reuses the `comment_review` setting. The whole public surface is gated by `guestbook_enabled` (default ON): when off, all three front endpoints reject with 「本站暂未开放留言板」 — **reads too**, mirroring `search_enabled` rather than only hiding the Vue entry — `SiteLayout.vue` drops the 留言板 nav item, and `views/site/guestbook/index.vue` renders a closed panel without fetching. Gating lives in `FrontMessageController` (the only consumer of `selectPublishedMessage*`/`insertMessage`), so admin moderation in `MessageController` (`/system/message`, perms `zhi:message:list|query|edit|reply|remove|export`) keeps working with the switch off — and admin replies still set status to published.
  **联系我们页咨询表单**（2026-10 新增）复用 `POST /api/message` 写入同一张 `zhi_message`，由独立开关 `contact_form_enabled` 控制（默认 ON；`FrontMessageController.add` 在「留言板或咨询表单任一开启」时放行提交，**读接口仍只受 `guestbook_enabled` 控制**）。表单结构化字段（公司/电话/咨询类型）由前端并入正文首部（`【咨询表单】…`），后台「留言管理」统一审核与回复，因此**不要为此新增表或列**；`verifyCode`/冷却/审核口径与留言板完全一致。
- Custom pages (自定义页面): public `GET /api/page/list` + `GET /api/page/{slug}` (`@Anonymous`, published only; slug detail increments `view_count`). Admin CRUD in `PageController` (`/system/page`, perms `zhi:page:*`). `slug` is unique and restricted to `[A-Za-z0-9_-]{1,100}`; `show_in_nav='1'` pages appear in the site navigation. 企业官网模式: setting `home_page_slug` (站点设置 → 站点信息「首页显示」) makes `/` and `/index` render that page instead of the article list (文章列表页路由为 `/news`) — both views render through `zhi-ui/src/views/site/page/CustomPagePanel.vue` (`minimal` prop = 首页模式, hides the Page badge + meta), the nav gains an 「文章」 entry pointing to `/news`（`route.name === 'PublicSiteArticleList'` 决定列表模式）。 A missing/unpublished slug falls back to the article list rather than showing a dead home page; nav menus are assembled by the pure `zhi-ui/src/utils/siteNav.ts` (honouring the three `nav_*_enabled` switches in both the top nav and footer quick links).
- Friend-link apply: public `POST /system/friendLink/apply` requires a graphic captcha (`code` + `uuid`, same switch as login: env `CAPTCHA_ENABLED` overrides `sys.account.captchaEnabled`) and is rejected with 「本站暂未开放友链申请」 when the `friend_link_apply_enabled` setting is off. Validate captcha through `ICaptchaService` (`CaptchaServiceImpl`, Redis key `captcha_codes:<uuid>`, single use) — reuse it for other anonymous writes rather than duplicating the logic.
- PV/UV detail: `zhi_visit_log` stores one row per content view (`VisitLogServiceImpl.recordVisit`, called from article view in `FrontController` and page view in `FrontPageController`) with `is_unique='1'` for a visitor's first view of that target that day (Redis `zhi:visit:day:<date>:<type>:<id>:<visitorKey>`, 48h TTL). Admin API: `/statistics/visit/list|summary|export|clean|{ids}` (perms `statistics:visit:*`). Retention is 90 days, cleaned daily at 01:10 by `DailyStatsSyncTask`. Note the intentional 口径 difference: `zhi_article.view_count` stays 24h-deduped while daily PV counts every visit and UV counts per-day unique visitors.

## Version Management (single source of truth)

Version is defined once in root `pom.xml` (`<version>` and `<app.version>`). When bumping, **must update** root `pom.xml` lines 9/24 AND the parent `<version>` in all 6 child poms (`zhi-common`, `zhi-system`, `zhi-framework`, `zhi-quartz`, `zhi-generator`, `zhi-admin`). Three further spots carry the number too and are easy to miss: the `${ruoyi.version:…}` fallback in `RuoYiConfig` (zhi-common), and `zhi-ui/package.json` + `zhi-ui/package-lock.json` (both the root `"version"` and the `packages[""].version` copy). Maven resource filtering replaces `@app.version@` in `application.yml`; `GET /system/version` serves it — and `.workflow/ReleasePipeline.yml` fails the tag build unless the pushed `vX.Y.Z` tag equals the root pom `<version>`, so bump the poms **before** tagging. See `docs/VERSION_MANAGEMENT.md`.

## Config / Env Gotchas

- Env vars come from `.env` (copy `.env.example`). Security-critical: `R_TOKEN_SECRET` (JWT, ≥64 chars), `DRUID_PASSWORD`, `REDIS_PASSWORD`, `DB_PASSWORD`.
- `SecurityConfigValidator` runs at startup: in prod it **blocks startup** if those are missing/weak; in dev it only warns. Set `SECURITY_VALIDATION_ENABLED=false` to bypass (dev only).
- Spring Security 6: use `requestMatchers()` / `authorizeHttpRequests()` / `SecurityFilterChain` — NOT Spring Boot 2 APIs.
- `spring.profiles.active` switches dev/prod; `captchaEnabled` controls captcha (disabled in dev). Env `CAPTCHA_ENABLED` overrides the DB switch.
- Feature switches share ONE rule (every read goes through these helpers — no hand-rolled `equals("true")` checks): only `false` / `"false"` / `"0"` / `0` means OFF; anything else (including a missing row) means ON. Frontend: `useSiteSettingsStore().isFeatureEnabled(key)` — never hand-roll the check in a page. Backend: `SiteSwitchUtils.isOn/isOff` (zhi-common). Server-side enforcement matters: `comment_enabled` rejects `POST /api/comment`（企业官网默认关闭，前台评论区与接口同时失效）, `search_enabled` short-circuits `/api/article/search`, `guestbook_enabled` short-circuits all three `/api/message/*` front endpoints, `view_count_enabled` skips counting + visit logging, `comment_review` decides the moderation status (comments and guestbook), `email_notify_enabled` gates comment notification mails, `referer_enabled` drives `RefererPolicy`. `SiteLayout.vue` loads the public settings by itself so footer/nav/copyright switches work on every page (pages that never fetch settings would otherwise fall back to store defaults).
- Security config validation reads Druid credentials as `spring.datasource.druid.stat-view-servlet.login-password` **with an env fallback** (`DRUID_PASSWORD`). Reading the property only made dev warn spuriously and **blocked production startup** whenever only `.env`'s `DRUID_PASSWORD` was set. The Druid console itself is intentionally not configured (the misplaced `statViewServlet`/`filter` block under `druid.master` and the never-loaded `application-druid.yml` were removed) — DB monitoring goes through Actuator/Prometheus/Grafana.
- `/error` must stay `permitAll` in `SecurityConfig`: filters that call `sendError()` (e.g. `RefererFilter` returning 403) trigger an ERROR dispatch, and if `/error` requires authentication RuoYi's unauthorized handler rewrites the response to `HTTP 200 + code 401`, masking the real status.
- Blog settings cache: `GET /common/site/setting` caches the aggregated map in Redis at `zhi:settings:all` (`CacheConstants.SETTINGS_ALL`, 600s TTL). **Every** path that writes `zhi_setting` must evict it (`@SiteCacheEvict(value = CacheConstants.SETTINGS_ALL)` on the controller method) — missing eviction makes admin toggles appear to have no effect on the frontend, which is why `SettingController`'s 5 write methods all carry the annotation. Note the mirror asymmetry in `updateByKey`: it copies the value into `sys_config` (the public read falls back to `sys_config` whenever the `zhi_setting` value is empty), but `SysConfigMapper.updateConfig`/`insertConfig` skip empty `config_value` via `<if test="configValue != ''">` — so a cleared setting (e.g. 「首页显示」 back to empty) would leave the OLD `sys_config` value behind and read back as if never cleared. The mirror row also can't be deleted (`configType='Y'` hits RuoYi's 内置参数删除守卫 in `SysConfigServiceImpl.deleteConfigByIds`), so `SettingController.applySettingUpdateByKey` clears it via the dedicated `SysConfigMapper.updateConfigValueByKey` (no `<if>` guard; `SysConfigServiceImpl` evicts `sys_config:<key>`), covered by `SettingControllerTest#testUpdateSettingByKey_ClearingValueClearsSysConfigMirror`.
- Monitoring entry URLs (admin monitor pages) are resolved at runtime by `zhi-ui/src/utils/monitorUrl.ts` (+ `monitorConfig.ts`): **站点设置** (`prometheus_url` / `grafana_url` / `actuator_url`, empty = auto) → **build-time `VITE_PROMETHEUS_URL` / `VITE_GRAFANA_URL` / `VITE_ACTUATOR_URL`** → **derived from the 站点访问地址 `blog_url`** (domain + 9090/3001; Actuator defaults to the same-origin `/manage/actuator`, which Vite/Nginx proxy in dev/prod). Never hardcode `localhost:9090` / `localhost:3001` / `localhost:8080` in monitor pages again, and do not put a `localhost` fallback in `.env.production` — Vite bakes it into the SPA, which is exactly why the Grafana page kept pointing at localhost on real domains. Production compose binds Prometheus/Grafana to `127.0.0.1` on purpose, so a public URL needs its own reverse proxy or tunnel. Also note `import.meta.env.VUE_APP_ENV` is never defined (Vite only exposes `VITE_*`, and the SPA cannot read container runtime env) — use `import.meta.env.PROD`/`MODE` instead.
- Client IPs (`IpUtils.getIpAddr`) are only taken from `X-Real-IP`/`X-Forwarded-For` when the **direct peer is a trusted proxy** (loopback or private range); otherwise the peer address wins, and the right-most valid XFF hop is used (spoofed prefixes are ignored). nginx must **override** rather than append (`proxy_set_header X-Forwarded-For $remote_addr`), and Vite's dev proxies set `xfwd: true` — without that, rate limits, the guestbook cooldown and the 24h view dedup are all keyed on a value the caller controls. Hotlink protection (`RefererFilter.isAllowed`) compares **hosts**: empty Referer and same-origin requests are always allowed, and a whitelist entry matches exactly or as a parent domain of the referer host (ports/scheme/path/case ignored). Never go back to `referer.contains(domain)` — substring matching lets `evil-example.com` or `example.com.evil.io` pass a rule for `example.com` (`RefererFilterTest` covers exactly these spoofs).
- Uploads go to `./uploadPath/` (project root, Docker mount point). **图片入库/渲染统一用站内相对路径**（`/profile/upload/...`，后端响应的 `fileName`）：`/common/upload` 返回的 `url` 是「请求 Host + 路径」的绝对地址，经 Docker/Vite 代理时会变成 `http://zhi-admin:8080/...`（浏览器解析不了、图片 404）。前端统一走 `zhi-ui/src/utils/uploadUrl.ts` 的 `normalizeUploadUrl()`：`ImageUpload` 只存 `fileName`，站点设置/导航/登录品牌区/首页 Banner/JSON-LD 等消费端渲染前收敛，历史脏值在设置页保存时自动写回（自愈）。不要直接使用 `res.url`。
- **「主题颜色」（`theme_color`）的适配边界**（2026-10 审计后固化）：
  - 应用链路：`utils/siteSettings.ts#initSiteSettings()` 读取主题色 → `handleThemeStyle()` 把 `--el-color-primary(-light/dark)` + `--mo-on-primary` 写到 `<html>` 内联样式。**读取时必须用 `readConfigValue()`**：`GET /system/config/configKey/theme_color` 经 RuoYi `AjaxResult.success(String)` 返回的是 `{ code, msg: "#409eff" }`（值在 **msg**，没有 data/configValue），直接取 `configValue` 会让主题色/Logo/侧边栏/自定义 CSS 全部静默失效（只有打开设置页才临时生效）——`siteSettings.test.ts` 已锁真实形态。
  - 登录后需再次应用：bootstrap 的 `initSiteSettings` 在无 token 时早退，`UnifiedLogin` 登录成功后会再调一次（不刷新页面也生效）。
  - 控件覆盖：mo-blog 主色控件（实心/plain 主按钮、Tabs 激活条、分页激活、侧栏菜单激活、TagsView、输入聚焦环、品牌 Logo 渐变）已改为 `var(--el-color-primary)` 派生，并用 `--mo-on-primary` 配前景色（亮主色→深墨、深主色→白）；**不要再把 Element 主色钉回 `--mo-p*` 字面量**。
  - **整条 `--mo-p*` 色阶由 `--theme-primary` 用 `color-mix` 派生**（`themes/mo-blog.scss` 的 `:root`）：`handleThemeStyle` 同时写内联 `--theme-primary`，所以改主题色 = 整站换色（含仍使用 `--mo-p*` 的旧页面/组件）；50–500 向白混合、700–900 向黑混合，档位比例对齐原靛蓝色板。深色模式的 `--mo-p50/p300/p500` 也改为按主题色向深底/白色混合（`theme-dark.css` 与各页深色块），`p600–p900` 仍不参与深色重映射（保持原约定）。

## Frontend Conventions

- **100% TypeScript.** All new code must be TS with types. Vite plugins in `vite/plugins/*.js` intentionally stay JavaScript — do NOT migrate them.
- **Auto-import**: `ref`, `computed`, `watch`, `onMounted`, `useRoute`, `useRouter`, Pinia APIs, etc. are auto-imported. Do NOT manually import them. Types in `src/auto-imports.d.ts`.
- Access Vite env vars with optional chaining: `import.meta.env?.VAR || 'default'` (can be undefined).
- API modules in `zhi-ui/src/api/` use the `request` wrapper; each has corresponding types in `src/types/api.d.ts`.
- HMR is enabled. If dev oddities persist, restart with `npm run dev -- --force`. Inside Docker (`DOCKER=true`) the dev server watches with `usePolling` because host-side edits on bind mounts (macOS/Windows) often deliver no inotify events — without it Vite keeps serving a stale module transform and edits look like they had no effect.
- **SVG icons must be strict XML.** `vite-plugin-svg-icons@2.0.1` parses every file in `src/assets/icons/svg/` with `svgo` at build time, and the `overrides` entry in `zhi-ui/package.json` hoists that `svgo` to **4.x** (the plugin declares `^2.8.0`) — svgo 4 parses strictly, so a single malformed icon fails `npm run build:prod` with an error that blames `zhi-ui/index.html` (the plugin scans while loading each module) instead of the offending file. This actually shipped: `button.svg` carried a duplicated `</path>` and only broke once svgo jumped to 4.x. `src/assets/icons/svg-icons.test.ts` re-parses every icon with the same parser and asserts tag balance, so a bad icon now fails `npm test` with the file name; re-check that test if you bump or drop the `svgo` override.
- **Dark-mode token contract (`--mo-*` scale is remapped, not preserved).** Inside `.site-layout` (and any page subtree with its own dark block) dark mode re-maps the scale in `src/assets/styles/theme-dark.css` (+ per-page copies in `blog/index.vue`, `blog/article/detail.vue`): `--mo-n0/n50/n800/n900` become **backgrounds**, `--mo-n100/n200/n600` are the primary **text** colors, `--mo-n300/n400/n500` secondary text, `--mo-p300/p500` the theme accent — while `--mo-p600~p900` are **not** remapped and stay light-theme indigo. So a dark rule using `color: var(--mo-n50|n0|n800|n900)` (text painted in the background colour, ≈1.0:1) or `color: var(--mo-p600~p900)` (dark indigo on dark, ≈1.7:1) is invisible — this shipped on 关于/留言板/自定义页面/分类/标签/归档, and the Mo-Blog theme additionally mapped `--mo-n300/n400` to `#57534e/#78716c` (darker than the cards), which dropped the whole layout nav/footer/summary text to 1.99~3.65:1. The admin area has no `--mo-*` remap at all outside its own scoped blocks (e.g. the article editor), so admin dark rules must use `--el-*` tokens instead. `zhi-ui/src/views/site/dark-mode-tokens.test.ts` guards the public-side contract; verify real rendering with a headless browser rather than by reading the palette, since the effective value depends on the remap.
- **Primary-filled controls need a paired foreground.** The default theme's primary is bright (`#409eff` light / `#00d4ff` dark), so Element Plus's white button label only reaches 1.77~2.78:1. `--mo-on-primary` carries the readable foreground (chosen per contrast by `utils/theme.ts` `readableOnPrimary`, re-set by `handleThemeStyle`; `:root`/`html.dark` defaults in `variables.module.scss`, `html.theme-mo-blog` overrides it to white since the indigo primary is fine). `zhi.scss` wires it into primary buttons (pinning hover/active to the primary fill because the `light-3` variant is *darker* in dark mode), `.el-pager li.is-active`, radio/checkbox buttons; the blog's custom accent buttons reuse the same token.
- **Light mode has its own contract (pale tokens are decorative only).** In light mode the raw palette applies untouched, so `--mo-n300/n400` (`#d6d3d1/#a8a29e`) and `--mo-p200/p300` are *tints*: using them for `color:` yields 1.49~2.52:1 on white (this shipped on home meta, category/tag counts, archive meta, article-body links/code, toc hover — 169 elements in the default theme, 311 in Mo-Blog). Text uses `n500`/`n600` (secondary) and `p700` (accent, with an `html.dark` override back to `p300`); `--mo-primary-text` (= `color-mix(primary 55%, #000)` in light, `var(--mo-p300)` in dark) is for primary-coloured text on light surfaces. Element Plus's own `#909399` (secondary/info) and `#f56c6c` (error) are too pale on white, so `html:not(.dark)` overrides `--el-text-color-secondary`/`--el-color-info`/`--el-color-error` (dark values live in `html.dark`). The Mo-Blog footer is a dark surface in **both** modes, so its text needs the light tokens in light mode too (`html:not(.dark).theme-mo-blog .site-footer ...`). `zhi-ui/src/views/site/dark-mode-tokens.test.ts` also guards the light half (pale-scale-as-text, decorative empty-state icons excepted).

## Testing

- **Backend (JaCoCo)**: 60% line + 60% branch minimums enforced via `jacoco:check` in root `pom.xml` (BUNDLE rule). `zhi-admin` and `zhi-generator` set `jacoco.skip=true` (still run tests, no coverage gate). Report at `target/jacoco/index.html`.
- **Frontend (Vitest)**: `npm run test` runs `*.test.ts`/`*.spec.ts` files. Coverage thresholds enforced in `vitest.config.ts` (lines/statements ≥70, functions ≥75, branches ≥55), scoped to `src/stores|utils|api|components` `.ts` files. Tests live alongside source (e.g., `utils/validate.test.ts`).
- Quality: `mvn checkstyle:check`, `npm run lint:check`, `npm run format:check`.
- **Dependency gate**: CI (`ci.yml`) and release (`release.yml`) run `npm run audit` in `zhi-ui` right after `npm ci`, so only **production** dependencies can block a build/发布. The script is defined in `zhi-ui/package.json` as `npm audit --omit=dev --audit-level=high --registry=https://registry.npmjs.org` — **keep the registry pinned**, because this machine's default registry is npmmirror, which returns `404 [NOT_IMPLEMENTED]` for `/-/npm/v1/security/*`, so an unpinned `npm audit` errors instead of reporting. `.github/dependabot.yml` registers `maven` (root POM → whole reactor), `npm` (`/zhi-ui`) and `github-actions`, weekly, patch+minor grouped into one PR. Dependabot only runs on the GitHub remote — Gitee/`origin` gets no equivalent alert, and there is deliberately **no** OWASP dependency-check in CI (needs an NVD key, 30–60 min first sync); Maven CVE coverage is Dependabot's job. Keep root `<repositories>` free of authenticated repos, otherwise the maven ecosystem stops reporting silently.
- **Tests must assert behaviour, not source text.** Do NOT write `readFileSync('X.vue')` + `toContain('<SiteLayout>')` style assertions: they stay green when the template is refactored or a class renamed, and they catch no runtime problem. Mount the component instead (57+ files already do, with Element Plus stubs) or call the pure function and assert the observable result. An audit found ~31 such files; `views/site/{guestbook,page,friendLink,auth}` were converted — e.g. the custom-page test now asserts `<script>`/`onerror` never reach the DOM instead of grepping for the `sanitizeArticleContent` import. **Exception that stays source-level:** cross-artifact contract checks that compare two files by nature — `nginx.config.test.ts`, `settings-seeds.test.ts`, `ArticleListQueryShapeTest`, `MapperColumnSchemaContractTest`, `ControllerPermissionPolicyTest`, `svg-icons.test.ts`, `dark-mode-tokens.test.ts`, `design-layout.test.ts`, `mo-blog.test.ts` (say in a comment why behaviour can't cover it). `it.skip`/`describe.skip` and `expect(true)` are not allowed as placeholders (currently 0 in the repo): stub the missing environment API (e.g. `URL.createObjectURL` under jsdom) and assert, or delete the case.
- **`MapperColumnSchemaContractTest` (zhi-system) is the schema↔mapper gate.** It parses `sql/00_init_database.sql` (CREATE TABLE bodies *and* the guarded `ALTER TABLE … ADD COLUMN` upgrade blocks) and checks that every column a single-table mapper references exists. This is what a real prod outage needed: `zhi_message` was created without `create_by`/`update_by` while `MessageMapper` selected them, so 后台「留言管理」list + 审核 + 回复 all threw `Unknown column 'create_by' in 'field list'`, while the public guestbook POST (which never writes those columns) stayed healthy — no test or page surfaced it. Adding a column to a mapper (or a table to a mapper) means the script must carry it: put it in the `CREATE TABLE` **and**, for existing installs, in an idempotent `SET @has_x … information_schema.COLUMNS … PREPARE/EXECUTE` block (the pattern around `zhi_friend_link.email`). Keep the parser's alias filter (`as col`) and the "exactly one known table per mapper" rule when you touch it, or JOIN-heavy mappers turn it red for the wrong reason.
